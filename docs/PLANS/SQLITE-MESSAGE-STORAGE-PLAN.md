# SQLite Message Storage Migration Plan

## Overview
Migrate from ETS-based in-memory message storage to SQLite-based persistent encrypted message storage. This enables message history browsing with queries like "show messages from bob from yesterday" or "show the last 10 messages received."

## Key Requirements

1. **Persistent Storage**: SQLite database for message history
2. **Encryption**: All messages encrypted at rest using passphrase-derived keys
3. **Same Encryption**: Use the same passphrase/method as key storage
4. **Query Support**: Support time-based and user-based queries
5. **Backward Compatibility**: Maintain existing API surface where possible
6. **Optional Storage**: Users can enable/disable database storage for privacy (default: disabled)
7. **Runtime Control**: Enable/disable storage dynamically via console commands

## Current State Analysis

### Existing Components

1. **cryptic_chat_storage.erl**: Placeholder module with ETS-based storage
   - Already has schema documentation for SQLite tables
   - Currently uses ETS tables: `cryptic_messages`, `cryptic_contacts`, etc.
   - Has TODO comment: "Replace with actual SQLite when esqlite3 is available"

2. **cryptic_lib.erl**: Encryption infrastructure
   - `derive_key_from_passphrase/2`: PBKDF2-SHA256 with 100K iterations
   - `encrypt_keys/2`: ChaCha20-Poly1305 AEAD encryption
   - `decrypt_keys/2`: Corresponding decryption
   - Format: `[Salt:16][Nonce:12][Ciphertext+Tag]`

3. **cryptic_console.erl**: Message delivery handler
   - `deliver_message` receives: `{FromUsername, Message, Timestamp}`
   - Currently no persistent storage integration

4. **Passphrase Management**:
   - User passphrase collected via `cryptic_shell:get_password/1`
   - Stored in context map as `passphrase` key
   - Passed to `cryptic_lib:initialize_client_keys/2`

## Architecture Design

### 1. Database Schema

```sql
-- Encrypted messages table
CREATE TABLE encrypted_messages (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    from_user TEXT NOT NULL,
    to_user TEXT NOT NULL,
    encrypted_message BLOB NOT NULL,      -- ChaCha20-Poly1305 encrypted
    salt BLOB NOT NULL,                   -- 16-byte PBKDF2 salt
    nonce BLOB NOT NULL,                  -- 12-byte ChaCha20 nonce
    timestamp INTEGER NOT NULL,           -- Unix timestamp (seconds)
    message_type TEXT DEFAULT 'text',
    read_status INTEGER DEFAULT 0,
    created_at INTEGER DEFAULT (strftime('%s', 'now')),
    
    -- Indexes for common queries
    INDEX idx_to_user_timestamp (to_user, timestamp),
    INDEX idx_from_user_timestamp (from_user, timestamp),
    INDEX idx_conversation (from_user, to_user, timestamp)
);

-- Metadata table for tracking database version and key derivation params
CREATE TABLE storage_metadata (
    key TEXT PRIMARY KEY,
    value TEXT NOT NULL
);

INSERT INTO storage_metadata (key, value) VALUES 
    ('version', '1.0'),
    ('encryption', 'chacha20-poly1305'),
    ('kdf', 'pbkdf2-sha256'),
    ('kdf_iterations', '100000');
```

### 2. Encryption Strategy

#### Per-Message Encryption
- **KDF**: PBKDF2-SHA256 (same as key storage)
- **Iterations**: 100,000 (matching `cryptic_lib:derive_key_from_passphrase/2`)
- **Cipher**: ChaCha20-Poly1305 AEAD
- **Salt**: Unique 16-byte salt per message
- **Nonce**: Unique 12-byte nonce per message (generated by crypto lib)

#### Encryption Flow
```erlang
1. Receive message: {FromUser, ToUser, PlainMessage, Timestamp}
2. Generate random salt: cryptic_nif:rand_bytes(16)
3. Derive key: derive_key_from_passphrase(Passphrase, Salt)
4. Encrypt: {Ciphertext, Nonce} = cryptic_nif:aead_encrypt(PlainMessage, Key, <<>>)
5. Store: {Salt, Nonce, Ciphertext} in separate columns
```

#### Decryption Flow
```erlang
1. Read from DB: {Salt, Nonce, Ciphertext}
2. Derive key: derive_key_from_passphrase(Passphrase, Salt)
3. Decrypt: PlainMessage = cryptic_nif:aead_decrypt(Ciphertext, Key, Nonce, <<>>)
```

### 3. SQLite Integration

#### Library Choice: esqlite
- **Package**: `esqlite` (or `sqlitex` as alternative)
- **Reason**: Mature, well-maintained Erlang SQLite NIF wrapper
- **Installation**: Add to `rebar.config` deps

```erlang
{deps, [
    % ... existing deps
    {esqlite, ".*", {git, "https://github.com/mmzeeman/esqlite.git", {tag, "v0.8.2"}}}
]}.
```

#### Connection Management
- **Single connection**: Stored in process state (cryptic_console or dedicated storage process)
- **Initialization**: Open DB in `cryptic_chat_storage:init_storage/1`
- **Cleanup**: Close DB in `cryptic_chat_storage:close_storage/0`
- **Location**: Determined by `cryptic_lib:get_cryptic_dir/3`
  - Example: `cryptic_lib:get_cryptic_dir("alice", "localhost", 8443)` returns `"/Users/ttornkvi/.cryptic/alice/localhost_8443"`
  - Database file: `<cryptic_dir>/messages.db`
  - Full path example: `~/.cryptic/alice/localhost_8443/messages.db`

#### Internal Helper Functions

```erlang
%% Encryption/Decryption helpers
-spec encrypt_message(binary(), binary()) -> {binary(), binary(), binary()}.
encrypt_message(PlainMessage, Passphrase) ->
    Salt = cryptic_nif:rand_bytes(16),
    Key = cryptic_lib:derive_key_from_passphrase(Passphrase, Salt),
    {Ciphertext, Nonce} = cryptic_nif:aead_encrypt(PlainMessage, Key, <<>>),
    {Salt, Nonce, Ciphertext}.

-spec decrypt_message(binary(), binary(), binary(), binary()) 
    -> {ok, binary()} | {error, term()}.
decrypt_message(Ciphertext, Salt, Nonce, Passphrase) ->
    Key = cryptic_lib:derive_key_from_passphrase(Passphrase, Salt),
    case cryptic_nif:aead_decrypt(Ciphertext, Key, Nonce, <<>>) of
        error -> {error, decryption_failed};
        PlainMessage -> {ok, PlainMessage}
    end.

%% Time conversion helpers
-spec datetime_to_unix(calendar:datetime()) -> integer().
datetime_to_unix(DateTime) ->
    calendar:datetime_to_gregorian_seconds(DateTime) - 62167219200.

-spec unix_to_datetime(integer()) -> calendar:datetime().
unix_to_datetime(Unix) ->
    calendar:gregorian_seconds_to_datetime(Unix + 62167219200).

%% SQLite query builders
-spec build_time_range_query(string(), string(), integer(), integer()) -> string().
build_time_range_query(User1, User2, StartUnix, EndUnix) ->
    io_lib:format(
        "SELECT id, from_user, to_user, encrypted_message, salt, nonce, timestamp "
        "FROM encrypted_messages "
        "WHERE ((from_user = ? AND to_user = ?) OR (from_user = ? AND to_user = ?)) "
        "AND timestamp >= ? AND timestamp <= ? "
        "ORDER BY timestamp ASC",
        []
    ).
```

#### New Console Commands

```erlang
%% Add history browsing commands
parse_command("history " ++ Args) -> 
    {history_cmd, parse_history_args(Args)};
parse_command(":h " ++ Args) -> 
    {history_cmd, parse_history_args(Args)};

parse_history_args(Args) ->
    %% Examples:
    %% "from bob yesterday"     -> {from, "bob", yesterday}
    %% "from alice last week"   -> {from, "alice", last_week}
    %% "last 10"                -> {last_n, 10}
    %% "with bob last 20"       -> {conversation, "bob", 20}
    case string:tokens(Args, " ") of
        ["from", User, "yesterday"] -> {from, User, yesterday};
        ["from", User, "last", "week"] -> {from, User, last_week};
        ["last", NStr] -> {last_n, list_to_integer(NStr)};
        ["with", User, "last", NStr] -> {conversation, User, list_to_integer(NStr)};
        _ -> {error, invalid_history_query}
    end.

execute_command({history_cmd, Query}, State) ->
    Username = maps:get(username, State),
    Passphrase = maps:get(passphrase, State),
    
    Result = case Query of
        {from, FromUser, yesterday} ->
            cryptic_chat_storage:get_messages_from_yesterday(
                Username, FromUser, Passphrase
            );
        {last_n, N} ->
            cryptic_chat_storage:get_last_n_messages(Username, N, Passphrase);
        {conversation, PeerUser, N} ->
            cryptic_chat_storage:get_conversation(
                Username, PeerUser, N, Passphrase
            );
        _ ->
            {error, unsupported_query}
    end,
    
    case Result of
        {ok, Messages} ->
            display_message_history(Messages),
            {noreply, State};
        {error, Reason} ->
            cryptic_shell:print_error(
                io_lib:format("Failed to retrieve history: ~p", [Reason])
            ),
            {noreply, State}
    end.

display_message_history([]) ->
    cryptic_shell:print_info("No messages found.");
display_message_history(Messages) ->
    cryptic_shell:print_info("Message History:"),
    lists:foreach(fun display_single_message/1, Messages).

display_single_message({FromUser, ToUser, Message, Timestamp}) ->
    DateTime = cryptic_chat_storage:unix_to_datetime(Timestamp),
    TimeStr = format_datetime(DateTime),
    io:format("[~s] ~s -> ~s: ~s~n", [TimeStr, FromUser, ToUser, Message]).
```

## Security Considerations

### 1. Passphrase Handling
- **Never store plaintext passphrase**: Keep only in memory
- **Wipe from memory**: When process terminates
- **Re-prompt**: If passphrase lost (process restart)

### 2. Encryption Security
- **Unique salts**: Every message gets unique 16-byte salt
- **Unique nonces**: ChaCha20 generates unique nonce per encryption
- **Authentication**: Poly1305 MAC prevents tampering
- **Key derivation**: 100K PBKDF2 iterations resist brute-force

### 3. Database Security
- **File permissions**: Set to 600 (owner read/write only)
- **No plaintext**: All message content encrypted at rest
- **Metadata protection**: Consider encrypting from_user/to_user if needed
- **Secure deletion**: SQLite VACUUM after deleting messages

### 4. Attack Resistance
- **Offline attacks**: Strong KDF makes dictionary attacks expensive
- **Tampering**: AEAD authentication detects modifications
- **Known-plaintext**: ChaCha20 resists known-plaintext attacks
- **Side-channels**: Use constant-time operations from libsodium

## Performance Considerations

### 1. Encryption Overhead
- **Benchmark**: ~10-100µs per message (PBKDF2 + ChaCha20)
- **Optimization**: Consider caching derived keys (security tradeoff)
- **Batching**: Encrypt multiple messages in single transaction

### 2. Database Performance
- **Indexes**: Create on `(to_user, timestamp)` for common queries
- **Prepared statements**: Reuse compiled SQL for repeated queries
- **Connection pooling**: Single connection for console, consider pool for server
- **Write-ahead logging**: Enable SQLite WAL mode for concurrency

### 3. Query Optimization
- **Limit results**: Always use LIMIT in queries
- **Pagination**: Implement cursor-based pagination for large result sets
- **Caching**: Consider in-memory cache for recent messages
- **Lazy decryption**: Only decrypt messages that will be displayed

## Error Handling

### 1. Encryption Errors
```erlang
{error, encryption_failed}    % ChaCha20 encryption failed
{error, decryption_failed}    % AEAD authentication failed
{error, wrong_passphrase}     % Decryption succeeded but plaintext invalid
{error, kdf_failed}          % PBKDF2 key derivation failed
```

### 2. Database Errors
```erlang
{error, db_not_initialized}   % init_storage not called
{error, db_connection_lost}   % SQLite connection dropped
{error, db_write_failed}      % INSERT/UPDATE failed
{error, db_read_failed}       % SELECT failed
{error, db_corrupt}           % Database file corrupted
```

### 3. Recovery Strategies
- **Graceful degradation**: Display messages without saving on storage failure
- **Retry logic**: Retry failed writes with exponential backoff
- **User notification**: Warn user if message storage fails
- **Backup prompt**: Suggest backup before critical operations

## Conclusion

This plan provides a comprehensive roadmap for migrating from ETS to encrypted SQLite storage for chat messages. The design leverages existing encryption infrastructure (`cryptic_lib`), maintains backward compatibility where possible, and prioritizes security through per-message encryption with passphrase-derived keys.

Key benefits:
- **Persistent history**: Messages survive process restarts
- **Query flexibility**: Time-based and user-based filtering
- **Security**: ChaCha20-Poly1305 encryption with strong KDF
- **Consistency**: Same passphrase/encryption as key storage
- **Performance**: Indexed queries and efficient storage
- **Privacy control**: Optional storage with runtime enable/disable for sensitive conversations

The implementation can proceed incrementally, with each phase delivering testable, usable functionality.

## Database Storage Control

### Configuration

The database storage feature is **disabled by default** for maximum privacy. Users who do not want to save sensitive data on disk (even encrypted) can keep it disabled.

**Option 1: Command-Line Flag**

Enable database storage when starting the console:

```bash
./scripts/cryptic_console --username alice --enable-db
```

**Option 2: Runtime Commands**

Enable/disable storage dynamically during a console session using the `db enable` and `db disable` commands (see Runtime Commands below).

### Runtime Commands

Users can control database storage at runtime via console commands:

- **`db enable`** - Enable message storage (initializes database if needed)
- **`db disable`** - Disable message storage (new messages won't be saved)
- **`db status`** or **`db`** - Check current storage status

### Use Cases

**Example: Temporary Privacy Mode**
```
> db disable
Database storage disabled. New messages will not be saved.

[have sensitive conversation]

> db enable
Database storage enabled
```

**Example: Checking Status**
```
> status
  Username:         alice
  Server:           localhost:8443
  WebSocket:        Connected
  Engine:           Running
  Database:         Disabled (not saving)
```

### Implementation Details

- Database is only initialized when `db_enabled = true`
- Message delivery checks `db_enabled` before saving
- Enabling database at runtime calls `init_storage/4`
- Disabling only updates state flag (doesn't delete data)
- Status shown in console status display
